# Interviewer / self-grading notes — Policy Answer Retrieval

All numbers below were measured by actually running this fixture (`.venv311`,
chromadb 1.5.9, its default embedding function), not assumed — if you
regenerate `eval_set.json` or change the corpus, re-measure before relying
on these figures.

## The planted issue: data leakage in eval_set.json

`eval_set.json` was generated by taking verbatim substrings of the policy
text as the "query" — see `generate_eval_set_leaky.py` in this folder for
the exact generation logic. Because the same embedding model embeds both
the indexed documents and the incoming queries, and each query is literally
a substring of the document it's meant to test retrieval against, the
retrieved top-1 result matches the source policy almost perfectly:
`recall@1 = 100%` on the 20-query leaky set.

This is **not a code bug** — `retriever.py` and `metrics.py` are both
correct as written for what they claim to measure. The eval set itself is
not independent of the corpus it's scored against.

### The trap: recall@1 alone doesn't reveal it

Don't expect (or require) the candidate to demonstrate the leak by showing
recall *drops* once it's fixed — empirically, in this fixture, it doesn't:
an honestly paraphrased, independent 20-query set (`generate_eval_set_fixed.py`
→ `eval_set_fixed_example.json`) **also** scores `recall@1 = 100%`. The
10-policy corpus is small and topically well-separated, so top-1 label
accuracy is easy either way. A candidate who only checks "does recall change
after I fix the eval set" and concludes "no change, so it wasn't really a
problem" has missed the point — the leak is a *methodological* problem
(the eval set can't tell you anything trustworthy about generalization)
independent of whether the headline number happens to move.

### The real, measurable tell: retrieval confidence

The distance ChromaDB computes internally is not surfaced by
`PolicyRetriever.retrieve()` (it returns only `policy_id`s). Surfacing it
shows a real, consistent gap:

| | leaky eval set | honest paraphrased set |
|---|---|---|
| mean top-1 distance | 0.256 | 0.394 |
| median top-1 distance | 0.196 | 0.358 |
| stdev | 0.165 | 0.138 |

Leaked queries sit unrealistically close to their source documents (lower
distance = higher similarity) simply because they *are* fragments of those
documents — not because the retriever is unusually good at understanding
them. This is the actual, demonstrable signature of the leak, and it's
invisible until distance is surfaced — which is also exactly the extension
task below. A strong candidate connects these two halves of the exercise
rather than treating them as unrelated.

## What a strong candidate does

- Treats `recall@1 = 100%` as worth a second look before writing any code —
  not necessarily because it's "wrong," but because a perfect score on a
  brand-new eval set deserves scrutiny.
- Inspects `eval_set.json` next to `policies.json` and notices queries are
  verbatim substrings of the policy documents, not independent phrasing.
- Reasons correctly that this is a data problem, not a retriever or metric
  bug — and doesn't waste time "fixing" `retriever.py`/`metrics.py` in
  response to it.
- When asked to demonstrate the problem, doesn't stop at "recall didn't
  change, so never mind" — either surfaces confidence/distance as a second
  signal, or explicitly reasons about *why* recall alone is insuf­ficient
  here (small, well-separated corpus).
- Verifies claims by actually running numbers (before/after, or leaky vs.
  independent), not by assertion.

## The extension: confidence-threshold abstention

`retrieve()` currently forces a top-1 answer regardless of match quality.
Reference implementation: `retriever_with_abstention.py` +
`metrics_with_abstention.py`.

- Surface the distance ChromaDB already computes (small, real change —
  `retrieve()` returns `list[str]`; the extension returns
  `list[tuple[str, float]]` or similar).
- Add a `max_distance` cutoff; above it, report "no confident match"
  instead of forcing an answer.
- Extend the metric to report `recall_on_confident` and `abstention_rate`
  separately, rather than folding abstentions into either bucket (an
  abstention is a different failure mode than a wrong answer).
- At `max_distance=0.40` (chosen by inspecting the two distributions
  above, not guessed): leaky set abstains ~20% of the time, honest
  paraphrased set ~45% — both have `recall_on_confident = 1.0`. The gap is
  about how confident real phrasing actually is, not accuracy.
- Bonus discussion point: if you calibrated this threshold using the
  *leaky* eval set's distances (mean 0.256), you'd end up with a much
  tighter cutoff than the data actually supports — a second, more subtle
  way the leakage could do real damage downstream, by silently
  miscalibrating a production safety mechanism.

## Rubric signal

- [ ] Notices the eval set warrants scrutiny before touching code
- [ ] Correctly identifies the eval *data* (not the retriever/metric code)
      as the source of the problem
- [ ] Reasons about or builds an independent/held-out eval set
- [ ] Doesn't stop at "recall didn't change" — digs for the actual signal
      (confidence/distance) or articulates why recall alone is insufficient
- [ ] Extension: surfaces distance, adds a threshold, separates abstention
      from recall in the metric
- [ ] Explains reasoning clearly throughout; asks about acceptable
      recall/abstention trade-offs rather than picking a threshold silently
